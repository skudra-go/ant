# Migrations

Your Go structs are the source of truth. `diff` compares them with a stored snapshot and writes the difference as plain SQL. You review the file, edit it if you need to, and `up` applies it.

Generating needs no database, and every migration is ordinary SQL, so any tool can read the files and you can stop using ant's runner at any time.

ant runs migrations on PostgreSQL. Other dialects return `schema.ErrUnsupported` until v0.4.

## Starting a project

Go cannot load your structs from another module, so the CLI is a small program in yours.

```go
// cmd/migrate/main.go
package main

import (
    _ "github.com/jackc/pgx/v5/stdlib" // the database driver

    "github.com/skudra-go/ant/dialect/postgres"
    "github.com/skudra-go/ant/migrate"

    "example.com/app/models"
)

func main() {
    migrate.Main[models.AppDB](postgres.Dialect)
}
```

Then generate and apply the first migration:

```sh
export DATABASE_URL='postgres://user:password@localhost:5432/app?sslmode=disable'

go run ./cmd/migrate diff create_tables
go run ./cmd/migrate up
```

That leaves:

```text
migrations/
├── versions/
│   ├── 0001_create_tables.up.sql   runs once
│   └── schema.snapshot.json        what the models looked like
└── code/                           reruns when a file changes
```

Commit all of it. The snapshot is what the next `diff` compares against.

## Daily work

Change a struct, then:

```sh
go run ./cmd/migrate diff add_bio   # writes 0002_add_bio.up.sql
# read the file
go run ./cmd/migrate up
```

`diff --dry-run` prints the SQL without writing anything.

In CI, `check` fails if someone changed a struct without generating a migration. It needs no database.

```sh
go run ./cmd/migrate check
```

`status` lists every migration and where it stands, and `drift` compares the live database with what migrations describe.

To undo a change, write a new migration. There are no down migrations.

## How models become tables

The Go type decides the column, so the common cases need no configuration.

| Go type | PostgreSQL column |
| --- | --- |
| `string`, named strings | `text` |
| `int`, `int64`, `uint32`, `uint64` | `bigint` |
| `int32`, `uint16` | `integer` |
| `int16`, `int8`, `uint8` | `smallint` |
| `bool` | `boolean` |
| `float64`, `float32` | `double precision`, `real` |
| `time.Time` | `timestamptz` |
| `[]byte` | `bytea` |
| `[16]byte`, such as `uuid.UUID` | `uuid` |
| `ant.JSON[T]` | `jsonb` |
| `postgres.Array[T]` | `text[]`, `bigint[]`, and so on |

A column is `NOT NULL` unless the Go type can hold nothing: a pointer, `sql.Null[T]`, a `sql.NullString` and its siblings, `ant.DeletedAt`, or a slice. An integer primary key is generated by the database. A field tagged `ant:"-"` or `ant:"computed"` has no column.

Configuration covers the rest.

```go
func (Post) Configure(b *ant.ModelBuilder[Post]) {
    b.Column(&P.Title).Length(200)                 // varchar(200)
    b.Column(&P.Price).Precision(10, 2)            // numeric(10,2)
    b.Column(&P.Status).Type("post_status")        // any SQL type
    b.Column(&P.Views).Default("0")                // a SQL expression
    b.Column(&P.Search).Generated("to_tsvector('english', title)")
    b.Column(&P.Note).Nullable()                   // or NotNull()
    b.Column(&P.Code).Collation("C").Unique()

    b.Index(&P.AuthorID).And(&P.CreatedAt).Desc()  // composite, descending
    b.Index(&P.Slug).Unique()
    b.Index(&P.PublishedAt).Where("deleted_at IS NULL").Name("posts_live_idx")
    b.Index(&P.Tags).Using("gin")
    b.IndexExpr("lower(title)").Name("posts_title_lower_idx")
    b.Index(&P.Body).Include(&P.Title).Concurrently()

    b.Check("posts_views_positive", "views >= 0")

    b.BelongsTo(&P.Author).OnDelete(ant.Cascade)   // SetNull, Restrict
    b.BelongsTo(&P.Editor).NoForeignKey()          // keep the relation, skip the key
    b.BelongsTo(&P.Team).NoIndex()                 // skip the automatic index
}
```

More configuration, for when the database needs to know:

```go
b.Comment("Published articles")
b.Column(&P.Status).Enum("post_status", "draft", "live")  // a native enum type
b.Column(&P.Number).Sequence("post_numbers", ant.StartAt(1000))
b.Column(&P.Code).Fixed(4)                                // char(4)
b.Column(&P.Secret).Comment("Never shown").Sensitive()    // stays out of logs

b.PartitionByRange(ant.F(&P.PublishedAt))                 // see the partitioning recipe

b.ForeignKey(ant.F(&L.OrderID), ant.F(&L.Region)).        // a key of several columns
    References(ant.F(&O.ID), ant.F(&O.Region)).OnDelete(ant.Cascade)
```

Migrations create enums and sequences before the tables that use them. A new enum value is one `ALTER TYPE`. Removing a value needs a person, because rows may hold it, so `diff` warns and writes nothing for it. `drift` compares only the enums and sequences models declare, so a type created by hand does not count against you.

`ant:"default=0"` is a short form of `.Default("0")`, and `ant:"unique"` of `.Unique()`.

**A default means a zero field is left for the database to fill.** That is the rule for `ant:"default"`, and `.Default` follows it, so never put one on a field whose zero value means something. A `Floor` of `0.00` with a default of `-100.00` would silently become `-100.00`. Without a default, zero is written as zero.

A type with no obvious column stops `diff` with a message saying which field. Set `.Type(...)`, or have the type declare its own column, which suits a library type:

```go
func (Money) ColumnType(dialect string) string { return "numeric(19,4)" }
```

Relations become foreign keys. The two sides of `User.Posts` and `Post.User` are one key, and either side can configure it. Delete behavior is `NO ACTION` unless you set it, so nothing is deleted that you did not ask for. A many-to-many relation creates its join table, once. Foreign keys get an index unless another index already starts with that column.

`b.View("name")` models have no table: define the view in `migrations/code`. `b.ExcludeFromMigrations()` means something else owns the table. `b.Schema("sales")` creates that schema and qualifies everything.

Models on one table merge into one table definition, which is how `b.Discriminator` works, and a column only some of them declare allows NULL. Polymorphic relations, from `.Morph`, have no foreign key, since one column cannot point at several tables.

## What generated SQL does for you

**Warnings.** Anything that could lose data or fail appears as a comment above the statement, and in the command's output.

```sql
-- WARNING: this drops column users.bio and its data.
ALTER TABLE "users" DROP COLUMN "bio";
```

**New required columns work on tables with rows.** A new `NOT NULL` column takes the field's zero value in existing rows, then stops having a default, so the column ends up as the model declares it. Edit the value if zero is wrong.

```sql
-- WARNING: existing rows of users get 0 in age. Change the DEFAULT below to fill them differently.
ALTER TABLE "users" ADD COLUMN "age" bigint NOT NULL DEFAULT 0;
ALTER TABLE "users" ALTER COLUMN "age" DROP DEFAULT;
```

**Renames.** A new name looks exactly like a drop and an add, and only you know which was meant. In a terminal, `diff` asks. Elsewhere, say so with a flag, which you can repeat:

```sh
go run ./cmd/migrate diff rename_bio --rename users.bio=about
go run ./cmd/migrate diff rename_table --rename users=people
```

Without either, the file warns and shows the statement to use instead, so you can edit it by hand. Constraints and indexes follow a rename by themselves, and are renamed, not rebuilt. The new name must be one the models have and the snapshot does not, in the same schema, so a misspelled `--rename users=peple` stops `diff` with the names it could have meant, and writes nothing.

**Generated columns keep what depends on them.** PostgreSQL before 17 cannot change a generated column's expression, so a new one means dropping the column and adding it again, and the drop takes its indexes and constraints with it. The file drops them first and makes them again after, along with foreign keys that point at the column, or at a unique index rebuilt with it. Such a file must run whole or not at all, so every index in it is built in its transaction, even with `Concurrently()`, and a warning names each one that asked to be built online. To build one online anyway, give it a migration of its own.

```sql
DROP INDEX "badges_label_slug_idx";

-- WARNING: badges.slug gets a new expression, so it is dropped and added again, which rewrites the table and rebuilds its indexes and constraints.
ALTER TABLE "badges" DROP COLUMN "slug";
ALTER TABLE "badges" ADD COLUMN "slug" text NOT NULL GENERATED ALWAYS AS (lower(trim(label))) STORED;

CREATE INDEX "badges_label_slug_idx" ON "badges" ("label", "slug");
```

A column that stops being generated keeps its values, with `ALTER COLUMN ... DROP EXPRESSION`.

**Generated SQL is a starting point.** The file is yours. This is the usual reason to edit one: `slug` is required and unique, and the generated file would give every existing post the same empty value.

```sql
ALTER TABLE "posts" ADD COLUMN "slug" text;
UPDATE "posts" SET "slug" = lower(regexp_replace("title", '[^a-zA-Z0-9]+', '-', 'g'));
ALTER TABLE "posts" ALTER COLUMN "slug" SET NOT NULL;
ALTER TABLE "posts" ADD CONSTRAINT "posts_slug_key" UNIQUE ("slug");
```

The snapshot records the models, so an edit that reaches the same schema changes nothing else. `drift` confirms it did.

## Changes models cannot express

**By hand.** `diff --empty name` writes a blank file, for extensions, enum types, triggers, or anything else. Models and snapshot stay as they are. If the models changed too, `snapshot` accepts them.

**Views and functions.** Files in `migrations/code` run after the versioned ones, in name order, and again whenever they change, so the file stays the single definition of the thing and git keeps its history. Number them if one depends on another, as in `10_views/` and `20_functions/`. A file must be safe to run again.

```sql
-- migrations/code/10_post_stats.sql
DROP VIEW IF EXISTS post_stats;
CREATE VIEW post_stats AS SELECT ...;
```

**Data, in Go.** For changes SQL cannot express, register a migration. It runs in sequence with the files, once, in a transaction, and `tx` is your context bound to it.

```go
func init() {
    migrate.Register[models.AppDB](
        "0005_split_names",
        func(ctx context.Context, tx *models.AppDB) error {
            _, err := ant.Raw[any](tx, "UPDATE users SET ...").Exec(ctx)

            return err
        },
    )
}
```

Put it in a package that both `cmd/migrate` and any program calling `migrate.Up` import. A model describes today's schema, not the schema at that point in the sequence, so prefer `ant.Raw` in anything that will outlive a model change. For work too large for one transaction, add `migrate.NoTransaction`, and commit in batches.

**Statements that refuse a transaction.** `-- ant:no-transaction` at the top of a file runs it without one, a statement at a time. `.Concurrently()` on an index adds it for you. If such a file fails partway, `up` stops until someone has looked: see [below](#when-something-goes-wrong).

**Seed data.** `go run ./cmd/migrate seed` runs Go seeders, each in a transaction, with model hooks off. They run whenever you ask, so write them to be safe to repeat. `Config.SeedHooks` turns hooks on.

```go
func init() {
    migrate.Seed[models.AppDB]("roles", func(ctx context.Context, db *models.AppDB) error {
        _, _, err := db.Roles.FirstOrCreate(
            ctx,
            &models.Role{Name: "admin"},
            ant.Eq(&models.Roles.Name, "admin"),
        )

        return err
    })
}
```

For data that should track a file, such as a list of countries, use an idempotent `INSERT ... ON CONFLICT` in `migrations/code`.

**Tests and prototypes.** `db.EnsureCreated(ctx)` builds tables straight from the structs, and `db.EnsureDeleted(ctx)` removes them. `go run ./cmd/migrate reset` wipes a local database and applies everything. It asks for the database's name first, or takes `--confirm name`.

## Deploying

Embed the files, so a binary needs nothing beside it.

```go
// migrations/migrations.go
package migrations

import "embed"

//go:embed all:versions all:code
var Files embed.FS
```

`go:embed` refuses a folder with no files, so a new project needs a `.gitkeep` in each until it has migrations. `all:` is what makes that count.

Then one `main.go` works in both places. `Embedded` is used only when the `migrations` folder is not on disk, so in a repository `diff` writes real files, and in an image `up` reads the binary.

```go
migrate.Main[models.AppDB](postgres.Dialect, migrate.Config{Embedded: migrations.Files})
```

There are two ways to apply them.

**A separate step**, as in a Kubernetes job or a compose service that runs before the server. This is the safer choice, because a schema change does not depend on a code rollout, and a failure stops the deployment before anything changes. The [blog example](https://github.com/skudra-go/ant-examples/tree/main/examples/blog) does this.

**At startup**, which suits small deployments:

```go
err := migrate.Up(ctx, db, migrate.Config{FS: migrations.Files})
```

Either way, several instances can start at once. A PostgreSQL advisory lock lets one work while the others wait, then find nothing to do. Session locks do not survive a pooler in transaction mode, such as PgBouncer, so run migrations on a direct connection, or set `Config.NoLock` and make sure only one runs.

For a database ant cannot reach, `script` writes one SQL file for someone else to run. Each block checks the history table first, so it can run any number of times, and `up` agrees with the result afterwards.

## Working in a team

Two branches that each add a migration usually collide. ant catches each way this happens.

- **The same version number.** Every command refuses, and names both files. Renumber the one that has not been applied anywhere.
- **A snapshot merge conflict.** The snapshot's `latest` line changes with every migration, so this conflict is on purpose. Take either side, keep both migrations, renumber if needed, then run `snapshot`. It records the merged models with no new migration.
- **A clean merge that lost the snapshot.** `check` compares the snapshot's `latest` with the newest file, and fails if they differ.
- **A migration older than what ran.** `up` refuses an older pending migration, because it was written against a schema that no longer exists. Renumber it, or set `Config.OutOfOrder`. `Config.Name = migrate.Timestamped` makes collisions rare.

Long histories can be squashed. `squash` replaces every file with one baseline.

```sh
go run ./cmd/migrate squash
```

The new file starts with `-- ant:replaces 0040`. A database that has those migrations records it without running it, and a new database runs it, so no environment needs a special step. A database that had not reached `0040` is refused, and has to catch up from an older release first.

A squash writes from the models, so anything written by hand is gone from the file, such as extensions, triggers, and data. The command warns about this. `--keep` joins the old files instead.

## Adopting an existing database

ant does not generate structs from a database. The mapping is ambiguous: `text` could be a `string`, a pointer, a named type, or an enum, and foreign keys say little about which relations you want. A person, or an AI assistant, does this better, given a dump and a way to check the work. `drift` is that check.

Your database, and whatever runs it today, stays as it is until the last step.

**1. Dump the schema.**

```sh
pg_dump --schema-only "$DATABASE_URL" > schema.sql
```

**2. Write the models**, by hand or with an assistant. Add a `cmd/migrate/main.go` as [above](#starting-a-project), and start from [this prompt](#a-prompt-for-your-assistant).

**3. Compare until there is nothing left.** With no snapshot yet, `drift` compares the live database with the models, and names each difference.

```sh
go run ./cmd/migrate drift
```

```text
The database differs from the models. To match, it would need to:
  change column accounts.name: type character varying(50) to text
  add unique accounts_email_key on accounts
```

Each line is a change to make in a struct, not in the database. Read them as what the models have wrong. Tables you will not model go in `Config.Ignore`, or get `b.ExcludeFromMigrations()`. Repeat until it says `No drift`.

**4. Start the history.** Pick one.

From the dump, which is usually right, because new databases then get everything, including what models do not describe. `adopt` removes the psql commands recent `pg_dump` versions write, and records the snapshot.

```sh
go run ./cmd/migrate adopt schema.sql
```

From the models, if they cover everything:

```sh
go run ./cmd/migrate diff baseline
```

From your existing files, if you want to keep the history. Copy them into `migrations/versions`, then run `snapshot`. `0001_x.up.sql`, `0001_x.sql`, and `V1__x.sql` all work as they are, and `.down.sql` files are ignored. Goose and dbmate keep up and down in one file, so split those first, or a new database would run the down part.

**5. Tell each existing database that it is done.** This records the migrations as applied, without running them. It adds the `ant_migrations` table, and touches nothing else.

```sh
go run ./cmd/migrate baseline
```

From here on, `diff` and `up` work as usual.

You can also keep your current migration runner. Run `snapshot` instead of steps 4 and 5, and use only `diff` and `check`, which need no database. `Config.Name` and `Config.Parse` can write files your tool expects.

### A prompt for your assistant

Paste this along with `schema.sql`, and adjust it to your project.

````text
This is the schema of an existing PostgreSQL database, from pg_dump. Write Go
models for it using the ant ORM, in one file per table, in package models. Do not
change the database: the models must describe it exactly as it is.

Rules:

- Models are plain structs. Embed nothing unless every table really has id,
  created_at, and updated_at as bigint and timestamptz.
- Field names convert to snake_case column names, and type names to plural
  snake_case table names. If that gives the wrong name, use ant:"column=name" or
  b.Table("name") in Configure.
- A column that allows NULL must be a pointer or sql.Null[T]. A NOT NULL column
  must not be.
- bigint is int64, integer is int32, smallint is int16, boolean is bool, text is
  string, timestamptz is time.Time, jsonb is ant.JSON[T], bytea is []byte. For any
  other type, including varchar(n), numeric(p,s), date, enums, and domains, use
  b.Column(&X.Field).Type("the type as written") in Configure.
- Declare each model's field probe: var Users = ant.Fields[User]().
- A primary key named id is found by convention. For anything else use b.Key or
  b.CompositeKey. A key that is not an identity or serial column needs
  .NotGenerated(). If the constraint is not named table_pkey, add b.KeyName("name").
- For each foreign key, add a relation with b.BelongsTo, and the other side with
  b.HasMany where it is useful. Set .OnDelete and .OnUpdate to match. If the
  constraint is not named table_column_fkey, add .ConstraintName("name"). If the
  column has no index, add .NoIndex().
- A join table with only two foreign keys is b.ManyToMany(...).Through("table").
  With other columns, model it as a table.
- A unique constraint is ant:"unique", or b.Column(&X.F).Unique("name") if it is
  not named table_column_key. A unique index that is not a constraint is
  b.Index(&X.F).Unique().Name("name").
- Add b.Index for each index, with .Name, .Desc, .Where, .Using, and .Include as
  needed. Use b.IndexExpr for an expression.
- Add b.Check for each check constraint, using its name.
- Add b.Column(&X.F).Default("expr") for each default, and .Generated("expr") for
  each generated column.
- Views are b.View("name"). Leave triggers, functions, and types out of the models.
- A context struct embeds ant.Context, and has an ant.Table[T] field for each model.

Then I will run `go run ./cmd/migrate drift`, which lists every remaining difference
between the models and the database. When I paste its output, fix the models. Each
line says what the database would need to do to match, so the models are what is
wrong. Never suggest changing the database. We are done when it prints "No drift".
````

## Changing how it works

Everything has a default, and everything can be replaced through `migrate.Config`, passed to `Main` or `Up`.

| Field | Default | Purpose |
| --- | --- | --- |
| `Dir` | `migrations` | The folder |
| `VersionsDir`, `CodeDir` | `versions`, `code` | The two folders inside it |
| `FS`, `Embedded` | none | Read from `go:embed`, always, or when the folder is missing |
| `Source` | files | Replace storage entirely |
| `PerDialect` | off | Keep each dialect's files in `Dir/<dialect>` |
| `Name`, `Parse` | `0001_name.up.sql` | Write and read file names, with `migrate.Timestamped` built in |
| `Render` | `schema.Script` | Replace how a plan becomes SQL |
| `HistoryTable`, `HistorySchema` | `ant_migrations` | Where applied migrations are recorded |
| `DSN` | none | The fallback after `--dsn` and `DATABASE_URL` |
| `Skip` | none | Versions to leave unapplied |
| `OutOfOrder` | off | Let an older pending migration run |
| `Ignore` | none | Names for `drift` to overlook, such as `legacy_*` or `users.handmade_idx` |
| `NoLock` | off | Turn off the migration lock |
| `SeedHooks` | off | Run model hooks while seeding |
| `Out`, `OnApply` | quiet in `Up` | Progress text, and a callback per migration |

**Storage.** `Source` lists migrations from anywhere, such as a table or an object store. Implement `Store` as well for the commands that write.

```go
type Source interface {
    List(ctx context.Context) ([]migrate.Migration, error)
    Snapshot(ctx context.Context) ([]byte, error)
}
```

**File names.** `Name` chooses a new file's name, and `Parse` reads a version and name back.

**SQL.** `Render` receives the plan, as data, and can wrap the default:

```go
migrate.Config{Render: func(plan *schema.Plan, d schema.Dialect) (string, error) {
    text, err := schema.Script(d, plan)
    return "SET lock_timeout = '5s';\n\n" + text, err
}}
```

## Leaving ant's tooling

Nothing here needs ant to keep working.

- `migrations/versions` is plain SQL in a common layout. golang-migrate runs the `.up.sql` files as they are.
- `go run ./cmd/migrate script --plain` joins everything into one file for any other tool.
- `schema-dump` prints the whole schema as SQL, from the structs.
- The history table is an ordinary table you can drop.
- Queries do not depend on migrations at all.

## Commands

Commands in the first group need no database.

| Command | Does |
| --- | --- |
| `diff <name>` | Write a migration for what changed in the models |
| `diff <name> --empty` | Write an empty migration to fill by hand |
| `diff <name> --rename a.b=c` | Treat a change as a rename, repeatable |
| `diff <name> --dry-run` | Print the SQL and write nothing |
| `check` | Fail if models, snapshot, and files are out of step |
| `snapshot` | Accept the models as they are, with no migration |
| `adopt <dump.sql>` | Make a schema dump the first migration |
| `squash [name]` | Replace all migrations with one baseline, `--keep` to join them |
| `schema-dump` | Print the whole schema as SQL, `--snapshot` to use the snapshot |
| `inspect [table]` | List the tables and columns the models describe |
| `script` | Print all migrations as one idempotent file, `--plain` for other tools |

| Command | Does |
| --- | --- |
| `up` | Apply pending migrations, then changed repeatable ones |
| `up --to <version>` | Stop after this version |
| `up --dry-run` | Print what would run |
| `status` | List every migration and where it stands |
| `drift` | Compare the live database with the migrations, `--sql` for the fix |
| `db-show` | Summarize the live database: version, size, and tables |
| `baseline [version]` | Record migrations as applied without running them |
| `repair` | Accept changed files, clear failed runs, and forget missing files |
| `seed [name...]` | Run seeders |
| `reset` | Delete everything and apply all migrations, `--seed` to seed too |

Commands that need a database take `--dsn`, and otherwise read `DATABASE_URL`, then `Config.DSN`.

## When something goes wrong

**A migration failed.** It ran in a transaction, so nothing of it remains, and later migrations did not run. The error gives the file, the line, and the database's explanation. Fix the file and run `up`.

```text
ant: migration 0002_add_post_slug failed and was rolled back: ERROR: could not create unique index "posts_slug_key" (SQLSTATE 23505)
  Key (slug)=() is duplicated.
```

**A `no-transaction` migration failed partway.** Some of it may have run, so `up` refuses to continue. Look at the database, then pick one. If you undid what ran, or the file can run again, fix the file and run `repair`, then `up`. If you finished it by hand, run `repair`, then `baseline <version>`.

**`applied migration was changed`.** Someone edited a file that has already run. Put it back, and make the change in a new migration. If the edit truly changes nothing, such as a comment, run `repair`. Line endings do not count as an edit.

**`applied migration is missing`.** A file that ran is gone. Put it back. If this is a Go migration, make sure the program imports the package that registers it. `repair` forgets it, if it is gone on purpose.

**`drift` reports something you did on purpose.** If it should be permanent, add it to the models and run `snapshot`, or put it in `Config.Ignore`.

**`diff` wrote something you do not want.** Delete the file, and restore the snapshot with `git checkout migrations/versions/schema.snapshot.json`.
